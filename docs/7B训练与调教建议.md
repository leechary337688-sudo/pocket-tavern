# 7B 本地模型：实聊结论、调教与微调建议

> 对象：LM Studio 的 `qwen2.5-7b-instruct-uncensored`（GGUF）
> 日期：2026-11-27
> 结论先行：**先做提示词/采样调教；不建议把「7B 全参或大 QLoRA」当作第一优先级。**
> 本文的「训练」分两种：**调教**（提示词、历史、采样、输出闸，零成本）与**微调**（QLoRA，需下载权重和训练栈）。当前只完成了前者和真实验收，微调尚未开始。

## 一、这次真实测试做了什么

- 测试脚本：`dev/real-lmstudio.mjs`
- 真实后端：`http://127.0.0.1:1234`，模型 `qwen2.5-7b-instruct-uncensored`
- 场景：2 人房（程墨白 + 琥珀），`turnBudget=2`，玩家一句「程墨白，你怎么看这局？」
- 结果：`REAL LM STUDIO OK (13/13)`，约 3.0 秒，2 个请求，3 条角色消息。
- 通过项：发言人有名字、两位角色都接话、无尾 cue 泄漏、无 `【别人】` 串台、无「（我…」主语句、无 assistant/用户标题、第二个 Agent 的「此刻」是自己的场景、请求带 stop、采样符合后端。
- 发现并修掉的两个真实问题：
  1. 群聊欢迎语的 `speaker` 用了 card id，导致第二个 Agent 的历史标签错误，曾生成「程墨白…」的第三人称旁白；已改为角色名字。
  2. 第二个 Agent 的「此刻」沿用了房主场景；已改为每个 Agent 使用自己角色的 `scenario`。
- 仍不完美：**7B 会把 40–100 字写成 80–120 字左右的多段**，并且容易写内心独白；这是模型能力/采样问题，不是串台。

## 二、现在就能做的调教（优先级最高）

1. **默认一轮一人**：`turnBudget=1`。只有 14B/32B 或云端强模型再开 2–3；7B 开 2 位容易把两个人的语气混在一起。
2. **关自动接力**：`chainMentions=false`。点名由玩家明确写，别让模型正文里的名字触发下一位。
3. **温度 0.7–0.8**；`top_p 0.9`、`min_p 0.05`、`rep_pen 1.08–1.12`、`max_tokens 220–320`。太长就把 `max_tokens` 降到 180，别靠加长提示词硬压。
4. **看「组装预览」**：确认最后一条 system 是输出契约，历史里的别人都是 `【角色名】` user，当前玩家消息没有重复。
5. **7B 不要用「自动接力」当默认**；需要两人对话时，在群聊设置里显式选「一轮 2 位」，比让模型自己点名稳定。
6. **出现第三人称旁白时**：先点「重生成」；仍出现就把温度降到 0.65，并在角色卡「人格」里加一句「只写自己的动作和台词，不写其他角色的心理和动作」。
7. **长会话**：超过 12–16 条就换场景/开新局，或依赖应用的摘要/状态账本；7B 的长上下文注意力有限。
8. **本地模型只做冒烟/离线**：正式角色扮演优先 DeepSeek 云端；7B 适合验证界面、流式、插件和提示词链路。

## 三、要不要真微调？

| 目标 | 微调是否有效 | 说明 |
|---|---|---|
| 少串台、少代写 | 有一点，但提示词/输出闸更有效 | 输出闸已经能拦住大部分 |
| 稳定 40–100 字 | 有效 | 需要大量长度受控样本 |
| 固定角色声线 | 有效 | 每个角色至少 50–100 条高质量对话 |
| 提升文笔/智力 | 很有限 | 7B 基座上限；不如换更大模型 |
| 学会世界书设定 | 不推荐 | 用 RAG/世界书，不要塞进权重 |
| 去除安全限制 | 不建议 | 已有 uncensored 版本；合规风险高 |

**建议**：先积累 100–200 条「真实好回复」再考虑 QLoRA；现在直接训练只会把 7B 的缺点学得更牢。

## 四、如果决定微调：现实条件

本机：

- GPU：RTX 3070 Ti，8 GB；跑 LM Studio 时已占约 6 GB，只剩 2 GB。
- Python：3.13.2；当前没有 `torch/transformers/peft/trl/bitsandbytes`。
- LM Studio 里是 **GGUF 推理权重**，不能直接用于训练；要另外下载 HF safetensors。

结论：**8 GB 能跑 7B QLoRA，但很紧**。训练时必须退出 LM Studio 释放显存；`max_seq_length` 先从 1024 起，2048 很可能 OOM。建议用 **Python 3.11 的独立 venv**，不要用 3.13（部分 CUDA/量化轮子还没跟上）。

磁盘与下载：

- HF 权重约 15 GB；
- 训练环境 + 输出 adapter 约 5–10 GB；
- 合并/导出 GGUF 再约 15 GB。至少预留 40 GB。

## 五、数据格式（关键）

一条样本只训练**一个角色**的回复；其他角色统一放在 user 里，用 `【角色名】` 标记。这样和 App 的 Agent 视角一致。

```json
{"messages":[
  {"role":"system","content":"你正在「袖珍酒馆」中扮演「程墨白」……"},
  {"role":"user","content":"【琥珀】（笑而不语地端详他片刻）「我这人向来不急躁。」"},
  {"role":"user","content":"程墨白，你怎么看这局？"},
  {"role":"assistant","content":"（抬眸，目光从琥珀身上扫过）局面微妙。对方似乎有意拖延时间，在等什么变数出现。"}
],"meta":{"scene":"雾港账房夜谈","speaker":"程墨白","rating":"sfw"}}
```

规则：

- `assistant` 只能有一个角色；绝不包含别人的台词/动作。
- 长度按目标控制：40–100 字为主，少量 20–40 和 100–140 做边界。
- 10–20% 硬负例：模型容易代写、串台、写「（我…」、复读的样本，**只保留正确回复**，不要保留错误回复让模型学。
- 数据来源：自己实际聊出来的好回复；用「重生成/编辑」后保留最终稿；不要拿模型未经筛选的输出直接训练。
- 每个角色 50–100 条，至少 3 个场景；总 150–300 条起步。
- 按场景划分 train/eval，不要随机切分同一局对话，否则评估会虚高。

## 六、QLoRA 起步配置（未在本机执行）

```text
base: Orion-zhen/Qwen2.5-7B-Instruct-Uncensored (HF safetensors)
quant: 4-bit NF4, double quant
LoRA: r=16, alpha=32, dropout=0.05
target: q_proj,k_proj,v_proj,o_proj,gate_proj,up_proj,down_proj
seq: 1024（先跑通再试 1536/2048）
batch: 1, grad_accum: 8
lr: 1e-4, cosine, warmup 3%
epochs: 2–3
precision: bf16（3070 Ti 支持；OOM 再换 fp16）
gradient_checkpointing: true
train_on_responses_only: true（只算 assistant token 的 loss）
```

流程：

1. 建 Python 3.11 venv，安装 CUDA 版 PyTorch、`transformers/datasets/peft/trl/accelerate/bitsandbytes`。
2. 下载 HF 基座权重；先跑 20 条过拟合 sanity check，确认 loss 能降。
3. 正式训练 2–3 epoch；保存 adapter。
4. 合并 adapter → 转 GGUF（llama.cpp `convert_hf_to_gguf.py`）→ `llama-quantize Q4_K_M` → 放进 LM Studio。
5. 用同一套 40 条评测集对比：基座 / 调教后 / QLoRA 后 / DeepSeek。只看“串台、代写、长度、推进、重复”五项，不要只看文笔。

预计：数据准备 1–2 天；训练 1–3 小时（8 GB 可能更久）；评测半天。收益主要是“更稳定地像这个角色、长度更听话”，不是“变聪明”。

## 七、评测门槛（建议）

- 串台率 < 5%
- 代写/替别人说话 = 0
- 40–100 字命中率 ≥ 80%
- 连续 3 轮有推进 ≥ 80%
- 复读/模板化 < 10%
- 重生成率 < 15%

达不到就继续调提示词/数据，不要盲目加 epoch。
